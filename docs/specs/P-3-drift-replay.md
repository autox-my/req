## The replay

One GIF, `docs/architecture/drift/req-replay.gif`, telling the README's headline sentence ("a tool that flags every edit would
raise the alarm three times; req raises it once") as three steps.

- **Two panels side by side**, the same layout in both: req's overview diagram reduced to its parts. Each part is a box with
  its name; the Evidence box carries REQ-0010.
  - **Left, "Flags every edit":** a generic baseline that marks a part for re-check whenever a linked requirement's text
    changes. It is not a named tool, and the caption says it is a baseline.
  - **Right, "req":** marks a part only as `req satisfy` judged it.
- **Three steps, the three committed edits of `docs/architecture/drift/edits.json`**, in order: reword, loosen, tighten. At
  each step:
  - **Left:** the Evidence box turns red, and an alarm counter rises (×1, ×2, ×3).
  - **Right:** reword and loosen leave it holding; tighten frames it in red, as ADR 0052's red frame does. The right
    counter ends at ×1.
  - **A counter on each panel:** "Edit 1 of 3" and so on.
  - **A status chip with req's verdict word:** HOLDS, HOLDS (weakened), SUSPECT.
- **A terminal pane under each panel.**
  - **Right:** req's real line for the `src/bench.rs -> REQ-0010` link, read from that edit's committed `satisfy.txt`.
  - **Left:** the edit itself (statement before → after, read from `edits.json`), with no verdict.
  - Every word of req's output comes from those files, never typed.
- **Pacing:** a short hold on the starting state (all holding), about three seconds per step, and a longer hold on the final
  frame. Under about 25 seconds in all, loops. Width 1600 to 1800 px, so it is legible on GitHub at full width. Keep it
  under 3 MB.
- **Visual language:** the page's own. Colours and type follow `docs/drift.html`; the red frame matches the overlay's
  `security-group` red; no decoration that implies data the files do not hold.

## How it is made

- **A script, `tools/demo/drift_replay.py`** (Python standard library), reads `edits.json` and the three `satisfy.txt`
  files. It writes one HTML frame per step state (or one page that takes the state as a parameter), screenshots each with
  local headless Google Chrome (`--headless --screenshot --window-size=…`), and assembles the GIF with `ffmpeg` (palette
  generation for a clean GIF).
  - Both tools are on the owner's machine. Neither is a repository dependency, and neither runs in the gate or in CI.
  - The script refuses (non-zero, naming what is missing) when Chrome or ffmpeg is absent. It never falls back to another
    renderer.
- **A record, `docs/architecture/drift/req-replay.gif.json`,** as P-2's `.png.json` records do: the SHA-256 of each input
  file (`edits.json`, the three `satisfy.txt`), of the script and of the GIF, plus the Chrome and ffmpeg versions, the frame
  size and the frame count.
- **A test** (extend `tests/drift_demo.rs` or add one) fails when any recorded input's SHA-256 no longer matches its
  committed file, or when the GIF's own SHA-256 does not match its record. The GIF is regenerated by hand when it goes
  stale, and the test names the command.
- **Add `req-replay.gif` and its `.json`** to `DRIFT_ROOT_FILES` in `tools/graph/build_architecture.py`, so the drift
  directory's leftover check accepts them.

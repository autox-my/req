# 0046. A committed trace document is the graph contract, and a viewer is an asset

Extends ADR 0018 (committed projections) and ADR 0023 (`req check`), and gives ADR 0029 §7's "a human reads every pull
request" something legible to read. No new command, no `RULES_V` bump, no claim-schema or Baseline change, no address
moves: a projection is a view, and this decision adds no rule to Tier-1.

**Status: proposed.** The owner ratifies it by merging the pull request that carries it. Raised from a comparative
review of an adopter-surface tool (reqord, `f043777`) whose one capability req lacks is a readable graph. Date proposed:
2026-11-12.

## Context

`req trace` already prints the graph: "the outgoing edges, the **derived** incoming edges" for a selection. It also
emits a versioned document, `req.trace/1`, under `--format json` — but that document is stdout only, because `--out` and
`--check` are text projections (`src/main.rs:381`). So the data model for a graph exists, is versioned, and nothing
consumes it.

The gap is the reader. `docs/trace.md` is legible to the person who wrote the corpus; a product owner or an auditor gets a
matrix. A second requirements tool ships a dashboard for exactly this, and it is the one thing it does better.

The temptation is to generate an HTML or SVG graph directly from `trace --out`. That is how a view becomes a second
source of truth: the artefact is edited by hand once, then quietly stops matching the corpus — the drift this project
exists to name, reproduced inside its own deliverable.

## Decision

1. **The document is the contract; the viewer is an asset.** `req.trace/1`, on stdout, is frozen as the public graph
   document. A viewer reads it and never writes; it is never truth, and deleting it removes nothing from the corpus.
2. **Deterministic or not committed.** If a graph document is ever committed as a projection it must be byte-reproducible:
   nodes ordered by claim id, edge lists sorted, no timestamp, no randomness, no layout computed in floating point.
   Anything else makes `--check`'s "current" meaningless.
3. **Not a projection in this repository.** ADR 0018 §4 keeps the list deliberately small — a projection is committed
   where it is a **deliverable**, not as a cache of every view. req delivers no graph; an adopter whose product owner
   reads one may add the document to *their* `.req/projections`.
4. **Drilldown is `impact`, not a new query.** `req impact <id>` already answers nearest-first. If its shape is wanted
   as a document, it is an additive `req.impact/1` declared on `req impact --help`, not a new command and not a second
   graph.
5. **The viewer ships as an example, not a package.** `examples/graph/` — one HTML file, no build step, no dependency,
   opened from disk, reading a path the adopter names. It opens no socket and fetches nothing (REQ-0012).
6. **Compatibility is stated in the document.** `req.trace/1` gains fields additively; a breaking change is `/2`. A
   viewer built for `/1` says it cannot read `/2` rather than guessing, the way `render --check` reports another build's
   `rules_v`.

## Consequences

- An adopter can render the graph their product owner will actually read, without a server and without a second copy of
  the corpus.
- The graph cannot drift silently, because the committed thing is the document and the document is judged by `--check`.
- `req.trace/1` becomes a compatibility promise for the first time. It is already versioned and already has a `schema`
  field; this decision is what makes the version mean something to a consumer outside req.
- No rendered artefact enters `docs/`.

## Rejected

- **SVG from `trace --out`.** A second artifact format to pin, check and diff, for a rendering concern. SVG is a
  rendering of a document, not a document.
- **A force-directed layout in the generator.** Non-deterministic, so a committed graph could never be `CURRENT`.
- **A `req graph` command.** Each command is a contract on its `--help` page; the data is already answerable from
  `trace`, and a second command would be a second home for one question.
- **Committing the graph in req's own repository.** It would answer a question nobody in this repository asks, at the
  cost of a projection that must be regenerated by every claim change.

## Falsification

This decision is wrong if any of these is observed:

1. two runs over one corpus produce different bytes for the same `req.trace/1` document;
2. a committed graph passes `--check` after a claim change that alters an edge — the check is not sensitive;
3. a viewer writes to the corpus, or needs a network connection to render;
4. `req.trace/1` changes in a way a `/1` consumer cannot detect and report.
